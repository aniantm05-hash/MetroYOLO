# MetroYOLO — исследование подсчёта пассажиров

**Когда дообучение детектора ухудшает задачу, ради которой его обучали.**

По фотографии вагона YOLOv5 находит людей, а система переводит число детекций
в условный индекс загрузки видимой области. В работе проверялась гипотеза:
поможет ли небольшой специализированный датасет считать пассажиров точнее,
чем готовая COCO-pretrained модель?

![Результат выбранной модели из исходной работы: 11 детекций, индекс загрузки 55%](docs/assets/report/detection-11.png)

*Один из трёх исходных примеров применения выбранной модели. Рамки и числа
извлечены из отчёта без изменений; это результат исследования, а не макет интерфейса.*

## Что проверялось

Исследование включает четыре проверки, а не только запуск детектора:

1. **Готовая YOLOv5s:** установить исходную ошибку на 21 validation-кадре.
2. **Дообучение на 30 эпохах:** адаптировать pretrained веса к фотографиям метро.
3. **Короткий запуск на 10 эпохах:** проверить, решает ли уменьшение длительности обучения проблему.
4. **350 настроек постобработки:** проверить, можно ли исправить подсчёт порогами confidence,
   NMS IoU и ограничением числа рамок без нового обучения.

Итог исходной работы — оставить pretrained модель. Дообучение дало приемлемые
метрики детекции, но не улучшило прикладную ошибку подсчёта; короткий запуск
привёл к большому числу ложных и дублирующихся рамок. Согласно отчёту,
рассмотренная сетка параметров также не превзошла baseline.

## Эксперимент начинается с данных

102 фотографии, один класс `person`, split 81 train / 21 validation.
Первичная разметка создавалась YOLOv5s, переводилась в нормализованный YOLO-формат
и корректировалась вручную в Roboflow. Кадры без людей сохранены как отрицательные примеры.
Переданный архив содержит 838 рамок; 10 изображений имеют пустую разметку.

Здесь возникает важная проблема оценки: **baseline помогал создавать эталон,
с которым затем сравнивали модели**. Ручная правка снижает риск, но не доказывает
независимость меток. Это одно из объяснений, рассмотренных в исходной работе,
а не установленная причина различий.

## Дообучение: рамки лучше по учебной функции, подсчёт хуже по задаче

![Сравнение ошибки по данным исходного отчёта](docs/assets/reported-comparison.png)

В отчёте зафиксирован рост ошибки одного из дообученных запусков: **1,05 → 1,90 человека**.
Для выбранной вместимости 20 ошибка индекса загрузки меняется с 5,24 до 9,52 п.п.
Это примерно на 81% большая ошибка подсчёта по округлённым значениям отчёта.

При этом сохранённая финальная проверка 30-эпоховой модели даёт precision 0,766,
recall 0,654 и mAP@0.5 0,790. Эти числа нельзя автоматически превратить в вывод
«модель лучше для оценки загрузки»: критерий выбора должен соответствовать задаче.

**Откуда числа:** baseline повторно проверен на переданных данных; 1,90 сохранено
в тексте отчёта (стр. 31), без доступного checkpoint и per-image CSV этого запуска.
Диаграмма показывает результат исходной практики, а не новое сравнение обученных весов.
[Подробности экспериментов и происхождение результатов](docs/research/02-experiments.md).

## Как проходило обучение

Обучение начинается с yolov5s.pt: 30 эпох, 640 px, batch 16, SGD, seed 0, Tesla T4.
Лог сохранился, поэтому доступны все 30 измерений, а не только финальная цифра.

![Training box и objectness loss из исходного запуска](docs/assets/training-loss.png)

Box loss снижается, а objectness loss меняется менее равномерно. Это поведение
функции обучения; по нему одному нельзя установить качество подсчёта или причину ошибок.
Class loss в одноклассовом запуске равен нулю и не означает идеальную классификацию.

![Validation precision, recall и mAP по эпохам](docs/assets/training-history.png)

Кривые показаны без сглаживания. Detection-метрики растут с колебаниями,
но они не измеряют ошибку числа пассажиров. Значения mAP baseline в исходных
материалах нет, поэтому улучшение mAP относительно готовой модели не заявляется.

## Проверка короткого обучения и постобработки

Уменьшение длительности до 10 эпох проверялось как попытка избежать ухудшения
при обучении. В отчёте короткая модель описана как нестабильная: она выделяла
поручни, руки, фрагменты сидений и создавала лишние рамки. В сохранённом выводе
`10EPOCH` — среднее предсказание 36,19 против 7,57 человека по разметке,
ошибка 28,62 и максимальное отклонение 64.

В notebook есть конфликт имён: команда на 30 эпох и оценка с подписью `10EPOCH`
используют одну папку весов. Результат не выброшен из истории, но его привязка
к независимому checkpoint не считается подтверждённой.

Затем проверялась постобработка: 10 confidence × 7 IoU × 5 max_det = **350 сочетаний**.
По отчёту, ни одно не улучшило результат относительно baseline. Полный рейтинг
не сохранился, поэтому тепловая карта и «лучшие пороги» не дорисованы.
Код перебора сохранён и доступен для повторения.

Содержательный риск этого подхода: `max_det` способен ограничить число рамок,
не исправляя их смысл. Правдоподобное количество ещё не доказывает корректную детекцию.

## Что средняя ошибка скрывает на отдельных кадрах

![Подсчёт каждого из 21 validation-кадров](docs/assets/baseline-analysis.png)

Готовая модель точно считает 10/21 кадров; на 19/21 ошибка не превышает двух людей.
В худшем случае она выдаёт 11 вместо 16. В другом кадре с 14 людьми число совпадает:
количество людей само по себе не объясняет все ошибки.

**Средний confidence также не является качеством подсчёта.** В худшем кадре он равен
0,56, но у пропущенных людей вообще нет рамок, которые могли бы попасть в среднее.

Есть и обратная ловушка: один пропуск и одна лишняя рамка могут дать правильное
число. Поэтому хороший count MAE не исключает ошибок детекции. В дальнейшем нужны
разбор FP/FN, дублей и независимая проверка меток вместе с подсчётом.

[Визуальный разбор и все три исходных примера](docs/research/03-findings.md).

## Решение и следующий проверяемый шаг

В условиях исходной практики выбран pretrained baseline. Повторный запуск
воспроизвёл его округлённые агрегаты. Причины ухудшения после обучения не разделены
контролируемыми экспериментами: малый датасет, шум меток и teacher bias остаются
кандидатами на объяснение, а не доказанными причинами.

Следующий эксперимент — независимо разметить test, разделить сцены по источникам,
сохранить каждый checkpoint и сравнить модели на одинаковых изображениях.
Пороги подбирать на validation, окончательные выводы делать по test.

Индекс `100 × count / capacity` относится только к видимой области. Это не измерение
вместимости всего вагона; его ошибка пропорциональна ошибке подсчёта.

## Код и запуск

Исследовательский notebook сохранён. Его функции вынесены в Python-пакет:
детекция, обучение, оценка, подбор порогов, проверка YOLO-разметки и экспорт результатов.
Есть локальное приложение, CLI, тесты и конфигурация CI.

Python 3.10–3.12:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e '.[app]'
python -m streamlit run app.py
```

Исследование и исходные иллюстрации открываются без скачивания модели.
Для своих фотографий выполни `bash scripts/setup_yolov5.sh` и выбери режим детекции.
[Воспроизведение обучения и оценки](docs/REPRODUCIBILITY.md).

```bash
python -m pip install -e '.[dev,app]'
python -m pytest -q
python -m ruff check .
```
